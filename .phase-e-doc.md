## An argument is moved into the slot it names

Phase E of [issue #212](https://github.com/myuon/cove/issues/212) is the item
Phase D named as the first thing
[#122](https://github.com/myuon/cove/issues/122)'s production split would have
to decide: **where a call's arguments go.**

Phase D's finding was that one slot numbering bought none of the three
refusals Phase C predicted, because those refusals were never about the
numbering:

> Arguments are pushed in *declaration* order and become the callee's first
> slots without moving, while the numbering groups slots by region.

Two orders, and they agree only sometimes. `cove_ir::Function::param_slot` is
the first thing this phase added — the callee's half of the convention as a
*number* rather than as a stack, and the arrangement `lower::convention`
already makes, read back off the finished `Function` rather than described a
second time. `param_slots_agree` compares the two on every debug build of
every lowered program, because a backend that moves a word to the answer must
not be able to disagree with the pass that made it true.

### The choice, and why it is not a choice between equals

Two shapes were named. They are not two costs; one of them is a cost and the
other is a reachability question.

**A permutation at frame-open** costs work per call, on exactly the path
Phases A–D showed the whole prize is on.

**A convention that states each argument's slot** costs nothing per call, and
requires the caller to know the callee's layout. It cannot: a value
parameter's slot is `value_origin + rank`, and `value_origin` is
`scalar_frame_size` — a width of the callee's *whole body*, not a fact about
its signature. `cove_ir::Function::params` has said why for as long as it has
existed, where it explains why the parameter kinds are written out rather than
derived:

> a caller has to place its arguments before the callee exists: a recursive
> call is lowered before its own `Function` does.

A call site knows what the checker settled about each parameter's *type*,
which is its region. It does not know how many slots the callee's body will
need, and a recursive or mutually recursive call is lowered before the answer
exists. So the convention is not available at the call site as the numbering
stands, and what would make it available is a different numbering: **the
parameters first, in arrival order, and the regions after them.** Then a
parameter's slot is its argument index and nothing else, the caller can place
it, and nothing ever moves.

That numbering is legal — ADR 0028 decision 1 requires of a physically split
realisation only that it "derives every physical offset from the one frame
layout", and a per-slot table is a layout. What it costs is the *split*
realisation, which is the production `Vm` today: with the parameters
interleaved through the numbering, a region is no longer a run, so
`values = base - value_origin` stops being one subtraction per frame and
becomes one indexed load per slot access. That is the second number across the
dispatch loop that Phase D deleted, brought back as a table. It would cost
this backend nothing, because one array has no offsets to translate — and it
would cost `benches/arith`, the one row already on the wrong side of 1×,
on every `load-scalar` it executes.

So the two shapes are not two prices for one thing. One is a per-call cost on
the frames that need it and nothing on the frames that do not; the other is a
per-access cost on the backend that is in production. **The permutation is
what this phase took**, and the measurement below is what it costs.

### Whether the lowering could sidestep it, and for how much of the corpus

The third possibility is that the *lowering* choose slot numbers that already
match declaration order, so that no permutation is needed. It can, partly, and
the way it would is a **per-function region order**: the three regions are laid
out in whichever order that function's own parameters are grouped in, rather
than always scalars-then-values-then-places.

Measured over the corpus — the 97 programs the differential harness lowers,
`tests/e2e` and `examples`:

| | functions | share |
| --- | ---: | ---: |
| every argument already arrives at the slot it names | 519 | 85.5% |
| an argument has to move | 88 | 14.5% |
| — of which a per-function region order would place | 68 | 11.2% |
| — of which it would **not** | 20 | 3.3% |

and by call site, which is what a run actually pays:

| | call sites | share |
| --- | ---: | ---: |
| all | 757 | |
| naming a callee whose arguments move | 129 | 17.0% |
| still doing so after a per-function region order | 36 | 4.8% |

So the lowering closes about three quarters of it (68 of 88 functions, 93 of
129 sites) and cannot close the rest. A region order can place parameters that
are *grouped* by region in declaration order, and only when every region
before the last one holding a parameter holds nothing else — a scalar local
declared in a function whose value parameter comes first is enough to break
it. Interleaved parameters it cannot place at all.

That leaves it a partial optimisation of a mechanism that has to exist anyway,
and it is not taken, for two reasons that are both about where a cost lands.
It would make `scalar_origin` a per-function number rather than the constant
zero, which is one addition on `Inst::LoadScalar` in the production `Vm` — the
`arith` loop again — to save a permutation the measurement below prices at
less than that. And it would put a *layout* decision downstream of a
*declaration* order, which is the shape of rule ADR 0027 exists to refuse
elsewhere.

### What it costs, measured

`benches/sortedargs` and `benches/mixedargs` are one program written twice.
Same struct, same loop, same two calls a turn, same two parameters — declared
in the numbering's order in one and against it in the other, so the callee's
prologue swaps two words on one row and moves nothing on the other. Both
execute **71,428,601 instructions**, equal on both backends, so the difference
between the two rows is the permutation and nothing else.
